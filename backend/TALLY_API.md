# SRF — Tally Outstandings API

For the Tally development team. Tally pushes customer outstanding (pending bill) data to this API; SRF stores it and shows it in its admin panel.

## Connection

| | |
|---|---|
| Base URL | `https://<srf-api-domain>/api/v1/tally` (the exact URL is shown in SRF Admin → Tally Sync) |
| Protocol | HTTPS |
| Content-Type | `application/json` |
| Authentication | `Authorization: Bearer <API key>` on every request |
| Max body size | 10 MB, and at most 5,000 records per request |

The API key is generated by the SRF admin and shared with you separately. If it is regenerated, the old key stops working immediately.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/ping` | Check the URL and key |
| POST | `/outstandings/sync` | Push outstanding data |
| GET | `/outstandings/sync-status` | Check the latest sync, or one sync with `?sync_id=` |
| GET | `/outstandings/customers` | Read back the stored balance per ledger, to compare with Tally |

## POST `/outstandings/sync`

Send one record per pending bill (bill-wise outstanding), as in Tally's *Bills Receivable* report. Do not send only ledger totals.

```json
{
  "company": {
    "company_name": "SRF TRADES",
    "tally_company_guid": "a1b2c3d4-0000-0000-0000-000000000000",
    "financial_year": "2026-2027"
  },
  "sync": {
    "sync_id": "SYNC-20261112-001",
    "as_of_date": "2026-11-12",
    "sync_type": "FULL",
    "batch_number": 1,
    "is_last_batch": true,
    "total_records": 2
  },
  "outstandings": [
    {
      "ledger_name": "A4 Glass House",
      "ledger_guid": "f9e8d7c6-0000-0000-0000-000000001001",
      "ledger_code": "CUST-001",
      "gstin": "32ABCDE1234F1Z5",
      "phone": "9995500000",
      "voucher_number": "SKY/2755/26-27",
      "voucher_type": "Sales",
      "voucher_date": "2026-09-18",
      "bill_reference": "SKY/2755/26-27",
      "due_date": "2026-10-16",
      "original_amount": 10000.00,
      "paid_amount": 5854.00,
      "pending_amount": 4146.00,
      "bill_status": "PARTIALLY_PAID",
      "narration": ""
    },
    {
      "ledger_name": "A4 Glass House",
      "ledger_guid": "f9e8d7c6-0000-0000-0000-000000001001",
      "entry_type": "ON_ACCOUNT",
      "pending_amount": -1500.00,
      "narration": "Advance received"
    }
  ]
}
```

### `company`

| Field | Type | Required | Notes |
|---|---|---|---|
| `company_name` | string | Yes | |
| `tally_company_guid` | string | Yes | Tally's company GUID. Must be the same on every sync. |
| `financial_year` | string | No | For reference, e.g. `2026-2027` |

### `sync`

| Field | Type | Required | Notes |
|---|---|---|---|
| `sync_id` | string | Yes | Unique per sync. All batches of one sync share it. |
| `as_of_date` | date | Yes | The date the outstanding figures are as of |
| `sync_type` | string | No | `FULL` (default) or `INCREMENTAL` |
| `batch_number` | integer | No | Starts at 1. Default 1. |
| `is_last_batch` | boolean | No | Default `true`. Send `false` on every batch except the last. |
| `total_records` | integer | No | Number of records in the whole sync across all batches. Recommended: it lets SRF detect a lost batch. |

### `outstandings[]`

| Field | Type | Required | Notes |
|---|---|---|---|
| `ledger_name` | string | Yes | Tally ledger name |
| `ledger_guid` | string | Recommended | Tally's ledger GUID. With it, a renamed ledger is still recognised. Without it, ledgers are matched by name. |
| `ledger_code` | string | No | Alias / code |
| `gstin` | string | No | Used to match the ledger to an SRF customer automatically |
| `phone` | string | No | |
| `entry_type` | string | No | `BILL` or `ON_ACCOUNT`. Default: `BILL` when a bill reference or voucher number is sent, otherwise `ON_ACCOUNT`. |
| `bill_reference` | string | For `BILL`: this or `voucher_number` | Tally bill reference (Ref. No.) |
| `voucher_number` | string | For `BILL`: this or `bill_reference` | |
| `voucher_type` | string | No | `Sales`, `Credit Note`, `Journal`, … |
| `voucher_date` | date | For `BILL` | Bill date |
| `due_date` | date | No | Defaults to the bill date |
| `pending_amount` | number | Yes | Amount still pending. Positive = receivable (Dr). Negative = credit balance (Cr). |
| `original_amount` | number | No | Original bill amount |
| `paid_amount` | number | No | Amount received against the bill so far |
| `bill_status` | string | No | e.g. `PENDING`, `PARTIALLY_PAID` |
| `narration` | string | No | Up to 500 characters |

Formats:

- **Dates:** `YYYY-MM-DD`. Tally's `YYYYMMDD` is also accepted.
- **Amounts:** rupees with up to 2 decimals, as a JSON number (`4146.00`) or a string (`"4,146.00"`).
- **Overdue days / age:** not needed. SRF calculates them from `voucher_date` and `due_date`.
- **On-account balances** (receipts or advances not adjusted against a bill): send them as a record with `entry_type: "ON_ACCOUNT"` and no bill reference.
- **One bill, one record:** within a request, the same `bill_reference` may appear only once per ledger.

### FULL sync (recommended)

A full sync sends *every* pending bill of every customer ledger as of `as_of_date`. When its last batch arrives, it replaces everything SRF held before. A bill missing from a full sync is treated as settled.

- The previous data stays live until the last batch is accepted. A sync that fails midway changes nothing.
- A bill with `pending_amount` 0 is ignored.
- An empty `outstandings` array is valid and means nothing is pending.

### Sending in batches

For large data, split one sync into several requests with the same `sync_id`:

| Batch | `batch_number` | `is_last_batch` |
|---|---|---|
| First | 1 | `false` |
| Middle | 2, 3, … | `false` |
| Last | n | `true` |

If `total_records` does not equal the number of records received when the last batch arrives, SRF answers `422 RECORD_COUNT_MISMATCH` and keeps the previous data live. Re-send the missing batch, then the last batch again.

### INCREMENTAL sync (optional)

An incremental sync sends only the bills that changed. Each record adds or updates that one bill. To mark a bill as fully paid, send it with `pending_amount: 0`. Bills not mentioned are left as they are.

Run a full sync at least once a day even if incremental syncs are used, so the two sides cannot drift apart.

### Retrying

Every request is safe to send again:

- Re-sending a batch overwrites that batch; nothing is duplicated.
- Re-sending a sync that already completed returns `200` with `"already_processed": true` and changes nothing.
- To start over, use a new `sync_id`.

### Success response — batch received, more expected

```json
{
  "success": true,
  "message": "Batch 1 received — waiting for the rest",
  "status": "RECEIVING",
  "sync_id": "SYNC-20261112-001",
  "sync_type": "FULL",
  "batch_number": 1,
  "received_records": 800,
  "created_records": 800,
  "updated_records": 0,
  "settled_records": 0,
  "total_received": 800
}
```

### Success response — sync completed

```json
{
  "success": true,
  "message": "Outstanding data synchronized",
  "status": "COMPLETED",
  "sync_id": "SYNC-20261112-001",
  "sync_type": "FULL",
  "batch_number": 2,
  "received_records": 703,
  "created_records": 703,
  "updated_records": 0,
  "settled_records": 0,
  "total_received": 1503,
  "outstanding_bills": 1503,
  "outstanding_ledgers": 301,
  "outstanding_amount": 8972741.99,
  "unmapped_ledgers": 12
}
```

`outstanding_amount` should equal the grand total of Tally's Bills Receivable report. `unmapped_ledgers` is for information only: ledgers SRF has not yet linked to one of its customers. The data is still stored, and the SRF admin links them in the admin panel.

### Error response

```json
{
  "success": false,
  "error_code": "VALIDATION_FAILED",
  "message": "2 problem(s) in the outstandings — nothing from this request was stored",
  "errors": [
    { "index": 14, "field": "voucher_date", "message": "voucher_date must be YYYY-MM-DD" },
    { "index": 31, "field": "pending_amount", "message": "pending_amount is required" }
  ]
}
```

`index` is the position of the record in `outstandings`, starting at 0. If any record in a request is invalid, the whole request is rejected and nothing from it is stored.

| HTTP | `error_code` | Meaning |
|---|---|---|
| 400 | `INVALID_JSON` | Body is not valid JSON |
| 400 | `INVALID_PAYLOAD` | Body is not a JSON object |
| 400 | `VALIDATION_FAILED` | A required field is missing or badly formatted; see `errors` |
| 401 | `UNAUTHORIZED` | API key missing or wrong |
| 409 | `SYNC_CONFLICT` | This `sync_id` was started with a different `sync_type` |
| 413 | `PAYLOAD_TOO_LARGE` | Body over 10 MB — send in batches |
| 422 | `RECORD_COUNT_MISMATCH` | `total_records` does not match what arrived |
| 500 | `SERVER_ERROR` | Problem on the SRF side — retry later |

## GET `/outstandings/sync-status`

Without parameters it returns the most recent sync. Optional: `?sync_id=SYNC-20261112-001`, `?tally_company_guid=…`.

```json
{
  "success": true,
  "sync": {
    "sync_id": "SYNC-20261112-001",
    "sync_type": "FULL",
    "status": "COMPLETED",
    "company_name": "SRF TRADES",
    "tally_company_guid": "a1b2c3d4-0000-0000-0000-000000000000",
    "as_of_date": "2026-11-12",
    "batches_received": [1, 2],
    "total_received": 1503,
    "expected_records": 1503,
    "outstanding_bills": 1503,
    "outstanding_ledgers": 301,
    "outstanding_amount": 8972741.99,
    "unmapped_ledgers": 12,
    "error": null,
    "started_at": "2026-11-12T05:30:00.000Z",
    "completed_at": "2026-11-12T05:30:04.000Z"
  }
}
```

`status` is `RECEIVING` (batches still expected), `COMPLETED` or `FAILED`.

## GET `/outstandings/customers`

The balance SRF currently holds per ledger. Parameters: `page` (default 1), `limit` (default 100, max 1000), `tally_company_guid`.

```json
{
  "success": true,
  "as_of_date": "2026-11-12",
  "total_outstanding": 8972741.99,
  "customers": [
    {
      "ledger_name": "A4 Glass House",
      "ledger_guid": "f9e8d7c6-0000-0000-0000-000000001001",
      "ledger_code": "CUST-001",
      "pending_amount": 29164.00,
      "bill_count": 6,
      "mapped_to_customer": true
    }
  ],
  "pagination": { "total": 301, "page": 1, "pages": 4 }
}
```

## Quick test

```bash
curl -H "Authorization: Bearer <API key>" https://<srf-api-domain>/api/v1/tally/ping
```

A correct URL and key return `{"success": true, "message": "API key accepted", …}`.

## Suggested schedule

A full sync once or twice a day (for example at 9 am and after closing), or after every billing session. Please confirm what Tally can trigger automatically.
